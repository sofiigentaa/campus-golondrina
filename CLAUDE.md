## Project

`pf-frontend` ("Campus") — a Spanish-language online course platform with an AI tutor, built on **Next.js 16 (App Router) + React 19 + Tailwind CSS v4**. This is the frontend only; it talks to a separate NestJS backend (`pf-back`). Comments and UI copy are in Spanish (rioplatense); keep that convention.

## Commands

```bash
npm run dev      # dev server on http://localhost:3000 (also rewrites AGENTS.md — commit that change with your work)
npm run build    # production build
npm run start    # serve the production build
npm run lint     # eslint (flat config, eslint-config-next core-web-vitals + typescript)
```

There is no test suite and no test runner configured. Type-check with `npx tsc --noEmit`.

## Environment

`.env.local` (gitignored) holds:
- `NEXT_PUBLIC_API_URL` — backend base URL (defaults to `http://localhost:3001` if unset)
- `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` — Stripe **publishable** key (`pk_test_...`); the secret key lives only in the backend
- `NEXT_PUBLIC_COURSES_SOURCE` — optional. `mock` serves the catalog/player from `data/*.mock.ts` (UI work without the backend). Unset = backend. **Never set it in production.** In API mode a backend failure surfaces as an error; it never silently falls back to mocks.
- `NEXT_PUBLIC_CHAT_SOURCE` — optional. `mock` serves `/dashboard/chats` from `data/chat.mock.ts` (includes a per-course group room that the backend doesn't have). Unset = backend (`services/chat/`): direct messages only, alumno↔docente, over `GET /chat/contacts`, `GET/PATCH /chat/:otherUserId/...` and the `/chat` WebSocket namespace. **Never set it in production.**

- `NEXT_PUBLIC_GOLONDRINA_SOURCE` — optional. `mock` simulates the Golondrina back (`/golondrina/me/...`) in memory (`services/golondrina/golondrina.service.ts`). Unset = backend; without the back module the panel says so (404) instead of faking it. **Never set it in production.**

Pending work on both sides (and what is still mock) is tracked in `docs/PENDIENTES.md`.

Path alias: `@/*` maps to the repo root.

## Architecture

### Route groups define the "chrome"

The root `app/layout.tsx` is intentionally minimal (html/body + global providers). Each route group supplies its own layout:
- **`app/(marketing)/`** — public: landing, course catalog, course detail, login/register, checkout. Shares `Navbar` + `Footer`.
- **`app/(app)/`** — authenticated area (`/dashboard`): sidebar + topbar shell, wrapped in `RequireAuth`. `/dashboard/admin` (resumen, cursos, categorías, usuarios) adds `RequireRole(["admin","teacher"])`; teachers only see their own courses, and categorías/usuarios are admin-only. **Sólo el docente escribe cursos**: crear, editar (datos, precio, portada), módulos, lecciones y adjuntos son de TEACHER y únicamente sobre sus propios cursos (`cursos/nuevo` y `cursos/[id]` llevan `RequireRole(["teacher"])`). **El admin sólo elimina y restaura cursos** (en el listado ve "Ver", que abre el curso público, y eliminar/restaurar), y no modera reseñas. `RequireRole` is UX only — the backend is the real check: `@Roles(TEACHER)` on every content write, plus `assertCourseOwner` (only the instructor; the admin gets 403) and `assertCanRemoveCourse` (instructor or admin) in `pf-back/src/common/utils/`, with 403 messages meant to be shown as-is — see `adminErrorMessage`/`backendMessageOr` below. In usuarios the admin can't change their own role or delete themselves: that would lock them out of the panel with no way back from the app.
- **`app/(player)/courses/[slug]/learn/`** — the lesson player, also `RequireAuth`-gated. Its own route group so it gets no Navbar/Footer (full-screen, `LessonHeader` is the only bar); the URL is unchanged. The tutor opens from a header button there instead of the floating button.

Route groups add no URL segment. The catalog and course detail are deliberately public; only the player and dashboard require auth.

`/courses` and `/courses/[slug]` are `force-dynamic` and the landing uses `revalidate = 300`: in Next 16 an uncached `fetch` in a prerendered page runs at build time, so a backend that's down during the build would freeze an empty catalog. Admin writes to courses, categories and covers call the `revalidateCatalog` Server Function (`lib/revalidate-catalog.ts`, via `withCatalogRevalidation` in `services/admin/`) so the landing doesn't lag up to 5 minutes. Anything that needs the session (full syllabus, progress, the lesson itself) loads client-side, because the token lives in `localStorage` — `CourseLearningProvider` completes the course detail and `LessonPlayer` does the whole player.

### Backend contract adapter layer (`services/`)

The backend does not yet match its own contract, and **`services/` is where every discrepancy is absorbed so components stay clean**. Search for `TODO(back)` — each marks a place to simplify once the backend catches up.

- **`services/api-client.ts`** — the single HTTP client (`apiFetch<T>`). Handles base URL, `Authorization: Bearer`, `credentials: "include"`, tolerant envelope unwrapping (`{ data, message? }` vs raw), tolerant error-message extraction (Nest `{ error, message[] }`), and `ApiError` (with `status`; `status === 0` = network/CORS failure).
- **`services/auth/`** — `auth.service.ts` normalizes `access_token`→`accessToken`; `token-storage.ts` keeps the session in `localStorage` (keys `campus.token` / `campus.user`), every access SSR-guarded and try/catch-wrapped. The backend also sets an HttpOnly cookie, but JS never touches it and it's cross-domain in prod, so `localStorage` is the source of truth for route protection. `getGoogleAuthUrl(flow)` appends `?flow=login|register` (carried through OAuth as `state`): from `/login` Google never creates accounts, from `/register` it creates one if the email is new and rejects if it already exists. Failures come back as `/{login|register}?error=not_registered|already_registered`, mapped to a message by `services/auth/oauth-error.ts` and shown by `LoginCard` / `RegisterCard`. `services/auth/post-login-redirect.ts` is the single post-login destination for form login, register and Google (`?redirect=` if it's an internal path, else `/dashboard`); Google keeps it in `sessionStorage` across the OAuth round-trip. `safeRedirect` also rejects `//host` open redirects. **Cuenta dada de baja** (soft-delete del admin, `status !== 'active'`): el back responde 403 con `code: "account_disabled"` en login (sólo si la contraseña es correcta; con una incorrecta sigue "Credenciales inválidas"), registro, Google (`?error=account_disabled`) y en cualquier request con sesión abierta (`JwtStrategy`); el chat por WebSocket también la rechaza en el handshake. En el front, `services/auth/account-disabled.ts`: `apiFetch` con `auth` cierra la sesión y lleva a `/login?error=account_disabled`, y `LoginCard`/`RegisterCard` muestran `AccountDisabledAlert` (con link a `/contacto`) en lugar de los mensajes contradictorios "no existe" / "ya existe".
- **`services/dashboard/`** — aggregates `GET /course-enrollments/me`, `/lesson-progress/me`, `/subscriptions/me` (all Bearer-auth). `enrollment.progressPercent` is **derived server-side**: the backend recalculates it (and `completedAt`) on every `POST`/`PATCH`/`DELETE` to `/lesson-progress`. No client writes it — `PATCH /course-enrollments/:id` was removed for exactly that reason. To move a course's progress, complete lessons. `dashboard.service.ts` is the raw GETs; `dashboard.view.ts` maps them to what the dashboard components render and is the single place documenting what is **real** vs still **mock** (streak/achievements/hours have no endpoint; per-course lesson totals and the "continue learning" module/next-lesson aren't in `/me`; recommended courses need a catalog adapter that doesn't exist yet). `components/dashboard/DashboardDataProvider.tsx` fetches once under `RequireAuth` and shares it via `useDashboardData()`.
- **`services/courses/`** — `courses.raw.ts` is the backend's raw shape and `courses.adapter.ts` is the only place that maps it to the domain `Course` (`types/course.types.ts`). Fields the backend lacks (subtitle, rating, studentsCount, projectsCount, tags, instructor title) come out `null`/empty and the UI hides them rather than inventing values; `coverGradient` is a fallback when there's no `imageUrl`. `courses.service.ts`: `CLIENT_SIDE_FILTERING = true` because `GET /courses` ignores query params (full list, filtered/paginated in `courses.client-filter.ts`); `getCourseBySlug` resolves slug→id via the list; `GET /courses/:id` returns modules without lessons (`syllabusStatus: "modules-only"`), so `loadSyllabus` fetches `GET /lessons?moduleId=` per module — that requires a session, so without login only module titles show.
- **`services/progress/course-progress.service.ts`** — per-course enrollment + completed lessons (filtered from the `/me` endpoints), `setLessonCompleted` (PATCH if a record exists, POST otherwise) and `enrollInFreeCourse` / `ensureFreeEnrollment` (the backend accepts it for free courses, and for any course with an active Premium subscription, for an admin, or for the teacher who owns that course; anyone else without Premium — students and teachers on other teachers' paid courses — gets 402 and goes through checkout).
- **`lib/lesson-access.ts`** — the one lesson-access rule for the front (syllabus locks, player sidebar, player): admin, the teacher who owns the course (`isCourseInstructor`), enrolled, active Premium, or `lesson.isFree` (preview). **Un docente sólo tiene gratis los cursos gratuitos y los suyos**: en un curso pago de otro docente es un alumno más (compra o Premium). It mirrors the backend's `LessonsAccessService`, which is what actually nulls `content`/`videoUrl`; change both together. Opening an accessible lesson auto-enrolls when enrolling is free for that user (`shouldAutoEnroll`), and moving to the next lesson ("Siguiente" or the sidebar) marks the current one completed. Only the admin is kept out of the checkout (`BlockAdminFromCheckout`; the backend answers 403 on `create-intent`). Teachers can buy courses and Premium; buying their own course returns 409.
- **`services/uploads/`** — every Cloudinary upload is multipart with the field `file`; `apiFetch` skips `Content-Type` for `FormData` so the browser sets the boundary. `uploads.ts` holds accept strings, size limits (image 5 MB, PDF 20 MB), `validateFile` (UX only) and `uploadErrorMessage` (503 = Cloudinary not configured on the backend). `entity-images.service.ts` uploads course/category images, which need the entity id — create first, then upload. There is no manual image-URL field anywhere anymore.
- **`services/lessons/lesson-resources.service.ts`** — private lesson PDFs. The download URL is signed and expires in 10 minutes: request it on click and use it immediately, never store it (`LessonResources` opens the tab before the `await` so it isn't blocked as a popup).
- **`services/admin/`** — admin panel CRUD (courses, categories, modules, lessons, users: role changes and soft delete). Las métricas del Resumen salen de `admin-stats.service.ts` → `GET /admin/stats?days=7|30|90|365`, ya agregadas en SQL en el back (`pf-back/src/admin-stats/`): totales, período actual vs anterior, inscripciones por día, ingresos por mes (12 meses), top 5 y últimas inscripciones. El alcance lo decide el back por rol: el admin ve la plataforma y el docente sus cursos (el Resumen es visible para los dos). Los gráficos son ApexCharts v7 cargado bajo demanda (`apexcharts/core` + área/barras/leyenda) vía `components/admin/stats/ApexChart.tsx`, que relee los tokens `--color-chart-*` al cambiar de tema y pasa a modo compacto en contenedores angostos; cada gráfico va en `ChartCard`, con resumen en `aria-label` y tabla "Ver datos". `lib/csv.ts` exporta las ventas (separador `;` y BOM para Excel es-AR, fórmulas neutralizadas). `adminErrorMessage` shows the backend's 403 message as-is when it's one of ours (e.g. "Este curso no es tuyo: no podés editarlo."), falling back to a generic Spanish message only for Nest's raw defaults ("Forbidden resource" and friends — see `services/backend-message.ts`, also used by `uploadErrorMessage`). Course/category/image writes go through `withCatalogRevalidation` (`services/admin/catalog-revalidation.ts`) so the landing (`revalidate = 300`) picks up the change immediately instead of within 5 minutes.
- **`services/profile/`** — perfil propio (`GET /users/me`, `PATCH /users/me`, `PATCH /users/me/password`), que alimenta `/dashboard/configuracion`. `GET /users/me` devuelve los datos personales más `hasPassword` e `isGoogleAccount`: una cuenta creada con Google no tiene `passwordHash`, y la sección de contraseña se adapta para dejarla crear una sin pedir la actual. El email no es editable — mandarlo (o mandar `role`) devuelve 400 por `forbidNonWhitelisted`. Las reglas de validación viven en `services/auth/validation-rules.ts`, compartidas con el registro.
- **`services/reviews/course-reviews.service.ts`** — reseñas: `GET /courses/:id/reviews` (público, paginado, con `summary` de promedio y distribución) y la propia por `/me` (`GET`, `PUT` upsert, `DELETE`). Sólo puede reseñar quien **terminó el curso** (inscripción activa + `enrollment.completedAt`, o sea lecciones al 100% y todos los checkpoints aprobados) y no es el instructor; el back lo decide y `GET .../me` devuelve `canReview` + `reason` (`not_enrolled` | `not_completed` | `own_course`) para que la UI explique por qué no. Nadie borra reseñas ajenas (tampoco el admin). Los comentarios se moderan en el back (`pf-back/src/moderation/`) en dos capas: una lista local de groserías con sus disfraces (leet, asteriscos, letras separadas) que corre siempre, y la IA de Groq (`openai/gpt-oss-safeguard-20b`, reusa `GROQ_API_KEY`) contra una política propia; lo ofensivo se rechaza con 422 y un mensaje genérico, la crítica negativa respetuosa se publica. Si la IA falla, pasa lo que ya pasó la lista (fail-open). `ReviewForm` conserva el texto ante un 422 y le da el foco al campo. `GET /courses` y `/courses/:id` traen `ratingAverage`/`reviewsCount`/`studentsCount` (agregados, no columnas). Filtro `?valoracion=` y orden `?orden=valorados|populares` son client-side en `courses.client-filter.ts`; "mejor valorados" usa promedio bayesiano contra el catálogo completo, así un 5★ con una sola reseña no le gana a un 4,8 con muchas. UI en `components/course/reviews/` (pestaña "Reseñas" de `CourseTabs`); al escribir se hace `router.refresh()` (promedio del hero) y `revalidateCatalog()` (landing).
- **`services/subscriptions/`** — `GET /subscriptions/me` (devuelve el historial completo; la vigente se busca con `findActiveSubscription`) y `PATCH /subscriptions/:id/cancel`. El alta no pasa por acá: la activa el webhook de Stripe. Cancelar **no** corta el acceso al toque: pasa `status` a `"cancelled"` pero el alumno sigue con Premium hasta `endDate` (deja de renovarse, no de valer). `isSubscriptionCurrentlyActive(status, endDate)` es la única regla que decide esto — la usan `findActiveSubscription`, `dashboard.view.ts` (badge PRO) y `checkout.service.ts` (no reofrecer pagar); el back la espeja en `SubscriptionsService.hasActiveSubscription` (pf-back), que es quien de verdad gatea inscripción a curso pago, contenido de lección, uso ilimitado del tutor IA y el conteo de "suscripciones activas" del panel de admin (`admin-stats.service.ts`, pf-back) — si cambia una, cambia todas.
- **`services/checkout.service.ts`** — Stripe PaymentIntent flow. Payment confirms in-browser; access is activated server-side by two independent paths: `/checkout/success` first calls `syncPayment(payment_intent)` → `POST /payments/:intentId/sync`, where the backend asks Stripe directly and activates if the charge succeeded (works with no webhook, e.g. on localhost), then polls `waitForAccessConfirmation`; the Stripe webhook remains as the backstop for users who close the tab before returning. `hasAccess` pre-check avoids showing the card form for something already owned (backend 409 is the real guard).
- **`services/chat/`** — chat en vivo alumno↔docente (directo únicamente; no hay sala grupal en el back). `chat.service.ts` es el único archivo que conoce el mock (`NEXT_PUBLIC_CHAT_SOURCE`) vs el back real: `GET /chat/contacts` arma la lista de conversaciones (agrupa por persona, no por curso — alguien puede compartir varios cursos con el mismo contacto), el historial sale de `GET /chat/:otherUserId/messages` y el envío va por el socket del namespace `/chat` (`chat.socket.ts`, singleton por pestaña, token en `auth.token` del handshake). Los mensajes nuevos llegan por el evento `message:new`; `ChatThread` los filtra por conversación. El chat no requiere Premium (cualquier alumno con el curso activo). `components/chat/ChatCenterProvider.tsx` (root layout) es el único dueño de la lista, los no leídos, la selección y el panel: lo consumen `/dashboard/chats`, el panel lateral `ChatPanel`, el aviso `ChatToast` (no sale si esa conversación está abierta), el badge del launcher y el "(n)" del título de la pestaña. `AuthProvider.logout` cierra el socket (`disconnectChatSocket`) para no dejarlo autenticado como el usuario anterior. **Admin↔docente** también chatea (soporte interno; admin↔alumno no): el back valida los pares en `ChatService.assertCanChat`. `getChatSocket` reusa la instancia mientras el token sea el mismo aunque el back la haya cortado — crear una nueva en cada llamada era el loop de 400 de socket.io en producción.
- **`services/speech/` + `hooks/useVoiceRecorder.ts` + `components/voice/`** — dictado por voz, opcional, en los composers del tutor IA (`ChatInput`) y del chat (`ChatComposer`). Graba con `MediaRecorder` (webm/opus; mp4 en Safari) y lo transcribe pf-back con Whisper en Groq (`POST /speech/transcriptions`, reusa `GROQ_API_KEY`; sin key, `GET /speech/status` da `available: false` y el micrófono no aparece). No se usa la Web Speech API porque no existe en Firefox, falla en Brave y en Chrome igual manda el audio a Google. El texto se **suma** al campo y queda para revisar: nunca se envía solo. Máximo 60 s; al terminar se apagan los tracks (si no, queda el punto rojo del navegador). Tres cosas que vienen de bugs reales y conviene no deshacer:
  - **Texto mientras se habla.** Cada 3 s se manda lo grabado hasta ahí y se muestra como provisional en la `RecordingBar`; al cortar, la transcripción del audio completo (que Whisper puntúa mejor) la reemplaza. Como en webm sólo el primer chunk trae los headers, cada parcial manda **todos** los chunks desde el principio, no el último. Un dictado de 30 s son ~10 llamadas, por eso `THROTTLE_SPEECH_LIMIT` es 60/min.
  - **Nunca descartar por nivel.** La primera versión tiraba la grabación si no superaba un umbral fijo (0,015) y mostraba "No te escuchamos": con un micrófono de auriculares la voz entra más bajo y se perdía todo. Ahora el umbral es relativo al ruido de fondo (medido en los primeros 400 ms) y ante la duda se manda igual; sólo se descarta el silencio absoluto (`SILENCE_RMS`), que es micrófono mudo o dispositivo equivocado.
  - **Selector de micrófono.** Sin `deviceId`, `getUserMedia` toma el predeterminado del sistema, que suele no ser el de los auriculares — la causa más común de "no me escucha". El elegido queda en `localStorage` (`campus.microphone`). Antes de grabar, el audio pasa por un `GainNode` con ganancia automática y un compresor (sólo amplifica si hace falta: con un micrófono normal la ganancia queda en 1), porque con señal muy baja Whisper devuelve cualquier cosa en vez de lo que se dijo.

### Client-side state

- **Auth** — `components/auth/AuthProvider.tsx` (React Context). `isLoading` starts `true`, resolves only on the client to avoid hydration mismatch. Revalidates against the backend on `pageshow` with `persisted: true` (bfcache) via `GET /users/me`. `RequireAuth` / `RedirectIfAuthenticated` do client-side route protection (replacing an old `proxy.ts` cookie check that fails cross-domain).
- **Theme** — `lib/use-theme.ts`, an external store via `useSyncExternalStore` (not React state), backed by `<html data-theme>` + `localStorage` + `prefers-color-scheme`. A blocking inline script in the root layout applies it before first paint.
- **AI tutor** — `components/ai-tutor/AiTutorProvider.tsx` (Context; a Zustand store was speced but zustand isn't installed). The drawer lives in the root layout so the tutor opens from any screen, via the single floating button `components/launcher/FloatingLauncher.tsx` (menu "Mensajes" + "Tutor IA" for students/teachers, tutor directly for everyone else; hidden in the player and on `/dashboard/chats`); `LessonTutorContext` feeds the current lesson id/title in. Connected to the real backend (`services/ai-tutor/ai-tutor.service.ts`): one conversation per lesson (the back requires a real `lessonId`, there's no general chat), so `LessonTutorContext` only mounts when `canView` is true — same access rule as the lesson content, so the tutor isn't a free way to discuss a paywalled lesson. The daily message limit of the Free plan is enforced server-side and shown in the drawer header; Premium/teacher/admin get `dailyLimit: null` (unlimited). `POST .../messages` today returns the whole reply as one JSON response, not a stream — a teammate has sketched a streaming + quick-actions (`action: SIMPLER_EXAMPLES | SUMMARIZE | ...`) contract that isn't implemented on any branch yet (confirmed via `git log --all -S`); when it lands, only `ai-tutor.service.ts` needs to change.

### Shared UI

`components/ui/ConfirmDialog.tsx` is the project's only real modal (`role="dialog"` + `aria-modal`, focus trap, ESC, scroll lock, focus restored to the opener). The existing side drawers (`AiTutorDrawer`, `DashboardSidebar`) predate it and have none of that — don't copy them for anything that interrupts the user to ask for a decision. `components/ui/input-styles.ts` holds the shared `inputClass(hasError)` used by every form. `ImageUploader` (avatar, course cover, category image), `UserAvatar` (photo or initial), `CourseCover` (image or gradient) and `ComingSoonLink` (nav item whose route doesn't exist yet — used via `comingSoon: true` in `DashboardSidebar` / `Navbar`) are the other shared pieces.

### Mock data

`data/*.mock.ts` provides course/dashboard/lesson/progress fixtures. Courses/lessons/progress mocks are only used with `NEXT_PUBLIC_COURSES_SOURCE=mock`. Achievements are real: the dashboard summary comes from `GET /me/dashboard` and `/dashboard/logros` from `GET /me/achievements` (every achievement with `actual`/`meta`; the back evaluates before answering, so catalog additions unlock retroactively). Categories, units and "te faltan N" live in `services/gamification/achievements.service.ts`; icons in `lib/achievement-icons.ts`. Streak and studied hours are real, from the temporary `GET /me/streak` / `GET /me/studied-time`, isolated in `services/progress/progress-stats.service.ts` + `use-progress-stats.ts` (consumed by `StreakCard`, `StudiedTimeCard` and the topbar pill) so swapping to the upcoming `GET /me/dashboard` touches only those files. `data/countries.ts` is generated by `scripts/gen-countries.mjs`.
